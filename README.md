# Codex + ChatGPT Pro + Claude Code 協作工作流

一套以 Codex 為協調者、ChatGPT Pro 網頁版為主要討論者、Claude Code 作為另一位對抗性審查者的有限回合協作方法。適合先讓不同工具提出、挑戰和修訂方案，再由負責人決定是否進入執行。

> 這是文件與提示詞範本，不是可安裝的整合程式。它不會自行呼叫 ChatGPT Pro、控制瀏覽器或啟動 Claude Code，也不保證服務商會在介面上提供特定模型或帳戶狀態。

## 這個工作流要解決什麼

- 把任務、輸入材料、討論次數和執行範圍先定清楚。
- 讓每位審查者都能讀到可核對的材料，並保留輸入與輸出的紀錄。
- 把「模型完成了回覆」、「審查循環完成」、「形成可供決策的方案」和「方案已執行」分開。
- 讓超時、材料不完整、模型身分不明等狀況明確停在待處理狀態。
- 不把模型彼此同意當成事實驗證，也不把建議當成執行授權。

## 角色配置

| 角色 | 工作 |
| --- | --- |
| 使用者／決策者 | 指定問題、範圍、驗收條件與執行授權；決定是否採用方案。 |
| Codex 協調者 | 整理材料、保存版本與雜湊、依順序傳遞意見、記錄回合並驗證交付。 |
| ChatGPT Pro 網頁版 | 提出初步分析，並在後續回合回應具體的審查意見。 |
| Claude Code | 作為另一位審查者挑戰假設、找出遺漏與失效條件。 |

建議把 Codex 對話放在主要工作區，把 ChatGPT Pro 網頁介面放在側邊面板，並在同一工作流程中使用 Claude Code CLI。實際可用性取決於當下產品介面、瀏覽器控制能力、CLI 登入狀態和使用者授權。介面不能讀取材料時，必須明確標示輸入未送達；不得假裝模型已看過。

## 快速開始

1. 複製 [工作流規格](WORKFLOW.md)，寫明目標、交付物、禁止事項、驗收條件，以及最多完整討論循環數和最多模型請求數。
2. 整理一份凍結的輸入材料包，記錄版本或 SHA-256；不要讓不同審查者看到不同版本而不留紀錄。
3. 依 [提示詞範本](templates/REVIEW-PROMPTS.md) 先取得 Pro 初步分析，再交由 Claude Code 審查，最後請 Pro 回應具體意見。
4. 用 [回合紀錄表](templates/SESSION-RECORD.md) 登記每次送出、實際收到的內容、錯誤、未解決分歧與狀態。
5. 整理成「供決策的候選方案」，由使用者決定是否執行。只有在使用者已明確授權的範圍內，才能開始執行。
6. 執行後以驗收條件和結果收據核對；沒有驗證的項目維持未完成或阻塞狀態。

## 回合與共識

本專案將一次實際送出的模型請求稱為「模型請求」。重試也要記錄，不能重設計數。開始前同時設定最多完整討論循環數和最多模型請求數，避免把「10 次請求」誤當成「10 個完整循環」。

一個討論循環可定義為「Pro 初步分析 → Claude 實質審查 → Pro 回應」。只有三個部分都收到可讀且有內容的結果，才計為完整循環。這仍不代表雙方達成共識：除非審查者明確確認剩餘意見已處理，否則協調者應稱為「候選方案」，逐項保留採納、拒絕和未解決意見。

## 驗證與限制

- 瀏覽器中的模型名稱、推理設定或訂閱標示只記錄介面實際顯示的內容；若服務沒有提供可驗證的後端資訊，就不要推定更強的身分證明。不同產品介面也不代表模型彼此獨立；證據不足時只稱為不同工具中的審查者。
- Claude Code 呼叫必須核對當次登入來源、正式結束狀態和實際回覆內容。單看「完成」不足以證明審查成功。
- 服務逾時或回覆被截斷時，標示為未知或阻塞。除非使用者明確批准，否則不自動重試、不換模型，也不改用付費 API。
- 有共識不等於真實。涉及事實、研究或程式行為的主張，仍須依任務所需的原始來源、可重現檢查或測試驗證。
- 不要把密碼、API 金鑰、私有檔案或不必要的個人資料放進公開紀錄。

## 範例成熟度

這份工作流源自一次有限的協作試行。可核對的紀錄包含一個完整的 Pro → Claude → Pro 討論循環；它沒有證明十輪討論、雙方最終確認或自動化整合已完成。因此本專案提供的是透明的流程範本，不宣稱這是一個已驗證的自動化產品。
